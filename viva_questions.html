Master Oral Defense Guide

QuizPulse: Viva & Code Defense Questions

Prepared specifically for defending QuizPulse in front of evaluators, professors, and external examiners.

Examiner Strategy Tip: Faculty members love asking "Why didn't you use React?", "How does the anti-cheat actually catch students?", and "What happens if internet disconnects?". Below are exact questions and the exact words you should speak.

1. High-Probability General Questions

Question 1 99% Probability
"What is QuizPulse, and what real-world problem does it solve?"
What the project does:
QuizPulse is a real-time, browser-based examination portal designed for teachers to conduct timed quizzes with zero student account setup overhead, zero cheating tolerance, and live monitoring.
Say this: "Sir/Ma'am, standard platforms like Google Forms lack live synchronous exam windows and anti-cheat enforcement. QuizPulse solves this: teachers build a quiz schema, generate a 6-character room code, and students join instantly using only their roll number and PIN. Once started, a strict 1-strike anti-cheat engine terminates the session if the student switches tabs, blurs the window, or leaves fullscreen."
Question 2 95% Probability
"Why did you use Semantic HTML, CSS, and Vanilla JavaScript instead of React, Angular, or Vue?"
Technical Justification:
Using Vanilla JS keeps the bundle size at virtually 0 KB, eliminates dependencies (no npm vulnerabilities, no node_modules bloat), and ensures 100% mastery over the native DOM and Browser APIs.
Say this: "We deliberately avoided heavy frameworks like React to adhere to pure Web Standards. Vanilla JavaScript loads instantaneously on slow student mobile devices, doesn't require a build or compile step, and gives us direct low-level control over browser APIs like Fullscreen API, Page Visibility API, and window blur events without framework abstraction overhead."
Question 3 90% Probability
"Explain the overall system architecture and data flow of your project."
Architecture Breakdown:
It is a serverless 3-tier web application:
  • Presentation Tier: Semantic HTML pages (index.html, teacher.html, student.html, quiz.html).
  • Logic & Anti-Cheat Tier: Pure JS engines (auth.js, app.js).
  • Data & Real-Time Tier: Cloud Firestore NoSQL Database via Firebase SDK with real-time WebSocket listeners (firebase.js).
Say this: "Our frontend runs as static HTML/JS files hosted on Vercel. All real-time synchronization—like the teacher starting the exam or monitoring student progress—uses Cloud Firestore's onSnapshot() listener. We don't need a Node.js Express server because Firestore acts as our real-time reactive backend."

2. Deep Technical & Code Questions

Question 4 95% Probability
"How does your Anti-Cheat system detect if a student is cheating? Which browser events are monitored?"
Code Explanation (app.js — line ~215):
The anti-cheat engine listens to 5 specific browser window/document events:
  1. document.visibilitychange: Fires when the student switches browser tabs or minimizes.
  2. window.onblur: Fires if the user clicks outside the browser or uses Alt+Tab to another app.
  3. document.fullscreenchange: Fires if the student presses Escape or exits fullscreen mode.
  4. document.oncontextmenu: Intercepts right-clicks (Inspect Element).
  5. document.oncopy / onpaste: Prevents copying question text to Google or ChatGPT.
Say this: "In app.js, we implemented armQuizAntiCheat(). We attach listeners to visibilitychange and blur. Under our strict 1-strike rule, any single trigger calls executeFinalSubmission(true, violationType), which instantly calculates their current score, marks the attempt as terminated for cheating, and locks the exam screen."
Question 5 85% Probability
"How do the dual timers work? What is Timer 1 vs Timer 2?"
Logic Explanation:
  • Timer 1 (Entry Window): Controls how long students can join the room after the teacher starts it (e.g. 5 minutes). Calculated as room.startedAt + entryWindowMinutes. Handled in student.html.
  • Timer 2 (Per-Student Attempt Duration): Countdown timer for answering questions (e.g. 15 minutes). Handled in app.js with setInterval(). When it hits zero, it auto-submits.
Say this: "Timer 1 is the lobby gatekeeper—once the entry window passes, latecomers cannot enter. Timer 2 runs inside app.js using setInterval() every 1000ms. It decrements seconds left, updates the progress bar, and when it reaches zero, it calls clearInterval() and submits the answers."
Question 6 90% Probability
"How does student authentication work? Where are student passwords stored?"
Security & Database Structure:
In this system, students don't create long-term Firebase Auth accounts. Instead, they authenticate with their Username/Roll Number and a temporary session PIN.
Say this: "To make student check-in fast, we use session tokens in Firestore. When a student enters their roll number and room code, a document is created in the rooms/{roomCode}/attempts/{rollNumber} collection. We store their session state in browser localStorage. If they refresh, the page recovers their draft from local storage so they don't lose progress."
Question 7 80% Probability
"How do you grade the student's submission? Client-side or Server-side?"
Grading Logic (app.js — line ~280):
The student's selected options in currentAnswers[questionIndex] are compared against question.correctOptionIndex.
let score = 0; for (let i = 0; i < questions.length; i = i + 1) { if (currentAnswers[i] === questions[i].correctOptionIndex) { score = score + 1; } } let percentage = (score / questions.length) * 100;
Say this: "During submission, calculateFinalScore() loops through all questions with a standard for loop. It increments score when the selected radio button index matches correctOptionIndex, and saves the score, percentage, and time spent to Firestore."
Question 8 85% Probability
"What happens if the student's internet drops while taking the quiz?"
Resilience Mechanism:
The app incorporates offline resilience through Draft Autosave:
  • Every time an answer radio button is clicked, saveDraftAnswers() writes the array to localStorage.setItem("quizpulse_draft_answers", ...).
  • If the browser disconnects or reloads, loadDraftAnswers() restores all chosen options.
  • Firestore's web client also queues writes locally and syncs back when connectivity restores.
Question 9 90% Probability
"Show me where the database schema is defined and explain its collections."
Firestore NoSQL Collections:
  • organizers/{email}: Stores teacher profile and password hash.
  • quizzes/{quizId}: Stores the quiz metadata (title, time limit, questions array).
  • rooms/{roomCode}: Stores the live room state (status: "LOBBY" | "LIVE" | "CLOSED", startedAt, entryWindowMinutes).
  • rooms/{roomCode}/attempts/{rollNumber}: Subcollection storing each student's score, answers, violation status, and timestamps.

3. Golden Rules When Answering

Golden Rules for Viva Success:

  • Rule 1: Always name the file first. Before explaining code, say: "We wrote that inside app.js" or "That's inside student.html". This instantly proves you know your directory structure.
  • Rule 2: Never say "the AI wrote it" or "the library did it". Say "We wrote a custom JavaScript event handler" or "We utilized standard Web APIs".
  • Rule 3: Show enthusiasm for pure vanilla code. Professors respect students who understand core fundamentals (DOM manipulation, event listeners, loops, async/await) far more than students who just copy React boilerplates.
